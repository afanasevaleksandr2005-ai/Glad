# Донат-магазин: кастомное оружие и форма → автовыдача в Arma 3

Схема для сервера «Грань войны»: игрок собирает оружие/экипировку на сайте
(конструктор как на референсе — база + слоты аттачментов), оплачивает через
ЮKassa/CloudPayments, и при следующем заходе на сервер (или в течение
~1 минуты, если он уже в игре) предмет выдаётся автоматически.

## Поток данных

```
[Сайт: конструктор]
   игрок выбирает базу + аттачменты (или комплект формы)
   цена считается на бэкенде по прайсу, НЕ по данным из браузера
        │
        ▼
[Бэкенд: создание заказа]
   INSERT в donate_orders (payment_status='pending')
   редирект на оплату (ЮKassa/CloudPayments)
        │
        ▼
[Платёжный вебхук]
   provider шлёт payment.succeeded → бэкенд помечает
   payment_status='paid', delivery_status остаётся 'awaiting'
        │
        ▼
[Сервер Arma 3 — extDB3]
   при коннекте игрока (и раз в ~60 сек для тех, кто уже в игре)
   SELECT заказы WHERE steam_uid=... AND payment_status='paid'
     AND delivery_status='awaiting'
        │
        ▼
[Миссия: fn_applyWeaponLoadout.sqf / fn_applyUniformLoadout.sqf]
   ID предметов из заказа сверяются со статическим whitelist'ом
   (никогда не берём classname напрямую из БД!), выдаются через
   addWeapon/addPrimaryWeaponItem/forceAddUniform и т.д.
        │
        ▼
[extDB3: UPDATE donate_orders SET delivery_status='delivered']
```

## Почему именно так

- **extDB3** — стандартное расширение для Arma 3, умеет ходить в MySQL
  напрямую из SQF (`"SQL_CUSTOM"` запросы) без своего HTTP-сервера.
  Если у вас уже есть сайт+БД — сервер Arma просто подключается к той же
  базе (или к отдельной read/write таблице `donate_orders`) через ODBC.
- **CBA_A3** (он почти наверняка уже стоит — от него зависит большинство
  модов) даёт `CBA_fnc_parseJSON` — безопасный парсер JSON, который **не
  исполняет код**. Это принципиально: `call compile` над строкой из БД —
  дыра для RCE, если кто-то подменит заказ в базе или перехватит запрос.
- **Whitelist предметов** (`config/items-whitelist.example.json`) —
  единственный источник classname'ов. Сайт хранит и присылает только ID
  (`"m4a1"`, `"acog_optic"` и т.п.), сервер сам мапит ID → classname.
  Так игрок физически не может вписать в заказ произвольный classname
  (читы, админ-предметы, несуществующие ID).
- **Цена всегда считается на бэкенде** по тому же whitelist'у при создании
  заказа — цену из тела запроса от клиента никогда не используем.

## Файлы в этом каталоге

- `schema.sql` — таблица заказов.
- `config/items-whitelist.example.json` — пример прайса оружия/аттачментов
  и комплектов формы. Замените classname'ами реальных модов вашего сервера.
- `server-integration/extdb3-example.ini` — пример конфига extDB3
  (SQL_CUSTOM-запросы, которые вызывает миссия).
- `server-integration/fn_checkDonateOrders.sqf` — опрос БД по Steam64 UID.
- `server-integration/fn_applyWeaponLoadout.sqf` — сборка кастомного оружия.
- `server-integration/fn_applyUniformLoadout.sqf` — выдача кастомной формы.
- `server-integration/initPlayerLocal-hook-example.sqf` — куда воткнуть
  вызов в существующей миссии (коннект + периодическая проверка онлайна).
- `backend-webhook/yookassa-webhook.example.js` — пример обработчика
  вебхука ЮKassa на Node.js (адаптируйте под ваш стек бэкенда — сама
  логика проверки статуса платежа и апдейта заказа переносится 1:1).

## Что нужно решить на вашей стороне

1. Какой стек у бэкенда сайта (для вебхука) — дайте знать, если нужен
   пример не на Node.js.
2. Реальные classname'ы оружия/аттачментов/формы из ваших модов — я взял
   плейсхолдеры (CUP/RHS-подобные названия), их нужно заменить на то, что
   реально стоит на сервере.
3. Где физически стоит extDB3 — на той же машине, что и Arma-сервер;
   нужен ODBC-доступ до MySQL сайта (или отдельная реплика/таблица).
